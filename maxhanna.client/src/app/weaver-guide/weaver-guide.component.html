🐝Overview

Weaver is an intelligent, agent-driven development environment that can modify your entire project from a single natural-language prompt.

Weaver understands your codebase, plans multi-step edits, applies atomic diffs, verifies its own results, runs terminal commands, searches the web, manages Git operations, and schedules recurring work — all from one integrated desktop application. It is designed to work with any OpenAI-compatible LLM backend — a local llama.cpp server, Ollama, or a hosted OpenAI-compatible API — and its iterative, verify-as-it-goes pipeline yields similar quality across small and large models alike.

🧠 Core Capabilities

  • One prompt → whole-project updates
  • Multi-file, multi-language edits (25+ languages)
  • Atomic, reviewable diffs with preview & Apply
  • Self-verification with an automated repair loop
  • Real web search + URL fetch as agent tools
  • Terminal control with an approval system

🗂 Built-in Panels

  • Kanban board (To Do / Doing / Done / Archived / Self-Improving)
  • In-browser IDE with file explorer & diff viewer
  • Calendar with cron automation
  • AI chat, Notes, Terminal, Meeting view
  • Benchmarks, rank ladder, suggestion engine
  • Voice-to-text input
👋 New to Weaver and not a programmer? Jump straight to the Using Weaver Without Writing Code guide and the Everyday Workflows recipes — email, web search, and scheduled cron jobs are covered step by step.

🚀Quick Start

  1. Run Weaver — launch Weaver.exe or run dotnet run from the repository root. Open the URL printed in the console (usually http://localhost:5000).
  2. Point it at an LLM — open Options → Settings → 🤖 Agent and set your default endpoint. Out of the box it expects an OpenAI-compatible server at http://localhost:8080 (llama.cpp or Ollama).
  3. Add a project — Options → ✎ Edit Projects, give it a name and the folder path of the codebase you want to work on. Make it the default if you like.
  4. Create a task — in the Kanban board, add a card to To Do, write what you want, optionally attach files for context, and press Start.
  5. Watch it work — the Agent panel streams the plan, each edit, command, and verification live. Any diff it proposes can be previewed and applied or rejected.
💡 Tip: phrase tasks as what you want done, not how — "Fix the README to add a section about forced edits" is a great starter task. If a task is purely about changing a file, prefixing with "Fix the …" reliably routes it through the file-edit pipeline.

📁Projects

Projects map a friendly name to a folder on your machine. Everything the agent does — discovery, edits, commands, git — runs inside the selected project's root.

  • Add / edit / delete — via Options → ✎ Edit Projects. Each project can have a description and its own build command.
  • Default project — chosen in the Edit Projects panel; the app selects it on load.
  • Per-project configuration — build commands, file hints, and ignored directories are scoped per project.
  • Switching — use the project picker in the header; the board, IDE, and calendar all follow the selected project.

A project description is shown next to the picker so you can tell projects apart at a glance.

📋Kanban Board

The kanban is the heart of Weaver: cards represent tasks, and each card can be run by the agent.

Columns

ColumnPurpose
To DoTasks awaiting execution. Cards with READY are queued for the agent.
DoingCards currently being executed by an agent run.
DoneCompleted work. Finished cards automatically generate improvement suggestions (💡).
ArchivedHistorical cards — count toward your rank score.
Self-ImprovingCards that round-robin back for continuous improvement, refining themselves after each run.

Cards

  • Text — the task. Cards often include completion summaries and context from their source (suggestion cards, cron cards).
  • Priority — low / medium / high, color-coded.
  • Attached files — provide discovery context for the agent.
  • Auto toggles — auto-queue, auto-test, auto-PR per card.
  • Tags — ⏰ SCHEDULED (came from a calendar cron), 💡 SUGGESTION (came from the suggestion engine), READY, QUEUED, and benchmark tags.

Running a card

Select a card and press Start. The Agent panel streams everything live: thinking, the step-by-step plan, each edit or command, verification results, and a final summary. Multiple agents can run concurrently — each run shows its own header with endpoint, task, progress, and log.

Meta-plans & diffs

  • Complex tasks get a meta-plan (sub-plans with file chips) rendered on the card.
  • Edits appear in the plan with diff previews — you can preview, Apply, delete, or open each diff in the IDE before or after the run.
  • The plan list marks each step ✅/⬜ as the agent works through it.
💾 Your board is saved automatically — cards, tags, and logs survive reloads.

🤖Agent Pipeline

Weaver runs a verify-as-you-go loop: discover → plan → execute → verify → repair, one atomic step at a time.

Phase 1 — Discover

The agent enumerates the project tree, indexes files, and uses BM25 scoring to auto-read the files most relevant to your task. It may also consult file hints (keyword → file mappings) and your card's attached files. Discovery runs inside a dedicated sandbox (when active) and produces a project skeleton summary.

Context review

Before planning, the agent reviews what it discovered and shows a context review — you can auto-confirm or add guidance (steering) before the plan begins.

Phase 2 — Plan & Execute (interleaved)

Rather than planning everything upfront, Weaver plans one atomic step at a time, executes it, verifies it, and only then plans the next step. Each step is one of the enabled agent tools:

ToolWhat it does
_exploreRead specific files for reference
_discoverProject-wide context search (BM25 + AI)
_commandRun terminal commands (subject to approval rules)
_create_fileCreate new files
_sql_migrationGenerate SQL migration files
_web_searchSearch the web
_web_fetchFetch a URL's contents
_gitGit operations (commit, push, PR)
_rename_fileRename files
_delete_fileDelete files
_showDisplay text to the user

You can disable any tool in Settings → Agent → Agent Tools. ⚠ Disabling edit, create, or explore makes the agent unable to change or inspect files — most tasks will stall.

Thinking & complexity

  • Each step shows pre-plan reasoning and streaming "extended thinking".
  • A complexity score (0–100) is computed per task — it labels the task (Simple / Moderate / Complex…), caps thinking tokens, and estimates the number of atomic steps. Simpler tasks are solved with fewer, cheaper cycles.

Verification & repair

  • Between steps: the loop assesses whether each step actually landed (e.g. the file changed as planned) and re-plans if not.
  • Post-execution: a dedicated verifier checks the finished work against the task's explicit requirements and lists concrete issues.
  • Repair loop: up to 3 repair passes re-plan for unmet requirements. If a repair recycles a completed step, the loop re-proposes with corrective feedback naming the verifier's concrete unmet requirement.
  • Verifier triage: speculative or "phantom" complaints (symbols that actually exist, "might/could" wording) are filtered out and not fed back to the replanner.

Steering

While a run is active (or before it), type guidance into the Steer the agent box — e.g. "prefer the existing utility module" or "don't touch the API routes". Steering is fed into the next LLM call.

Logs & output

  • The Log panel keeps a timestamped activity log with levels (info / step / success / warn / error / metric) and expandable raw details with diagnostics.
  • LLM Streaming shows the raw token stream, with font-size controls.
  • Commands lists every executed step with side-by-side diffs for edits.
  • Files changed chips track what the run touched.
🧵 Resume & orchestrate: completed plan steps are persisted on the card. If verification found unmet requirements, resuming re-plans for those instead of declaring done.

💬Ask AI

The Ask AI panel is a chat with the agent, with two modes:

  • Ask — ask questions about the project; the agent can explore files to answer.
  • Build — a tool palette of quick actions that inject hints into your prompt for common operations (create files, fix formatting, add tests, and more).

Use it to ideate, get explanations, or kick off work without creating a kanban card first.

📝IDE

A full in-browser IDE with a file explorer, multi-tab editor, and git tools — everything the agent edits is right here for you to inspect.

  • File explorer — tree navigation with search; build/vendor folders (node_modules, bin, obj, .git, …) are hidden by default and can be revealed. Ignored dirs are configurable (Editor:IgnoreDirs, entries prefixed - un-hide a default).
  • Multi-tab editor — syntax highlighting for 25+ languages (C#, Java, C/C++, JS, TS, JSX/TSX, HTML, XML, SVG, CSS, SCSS, LESS, JSON, SQL, Python, Ruby, PHP, Go, Rust, Swift, Markdown, YAML, Shell, PowerShell, Kotlin…).
  • Dirty-state tracking and external-change detection (files changed outside the app are flagged).
  • Conflict detection — including BugHosted shared-editing indicators.
  • Search-in-file with match navigation.
  • Side-by-side diff viewer for reviewing agent edits.
  • Git integration — commit, push, and PR creation from the IDE.

The IDE is a floating panel — drag it by its header, resize from the edges/corner, and it remembers its geometry across reloads.

💻Terminal

Weaver can run terminal commands — for builds, tests, package installs, and anything the agent needs. Command execution is gated by the terminal approval system (see Terminal Security).

  • Type commands manually, or let the agent run them as _command steps.
  • Pending commands appear in an approval queue — approve once, approve the root command forever, approve all, or reject.
  • Output streams into the panel; the refresh button restarts the session.
⛔ In Approve all mode the agent runs any command without asking — destructive commands like rm -rf, git push, or DROP TABLE execute immediately. Keep an eye on what the agent is doing.

📒Notes

A floating note-taking panel for jotting context, TODOs, or scratch content alongside your work. Like the IDE, it persists its position and size.

🕷️Meeting View

A playful visualization of the agent's live run: domain spiders (planner, editor, verifier, …) animate across an office scene — climbing with rejected edits, cooling with success. The complexity spider's rage rises with every rejected edit, the verifier's smugness climbs with the same rejections, and each spider lights up in its role color once its grump crosses 50%.

  • Voiceover chatter is generated per role ("A QA spider walks into a bar…").
  • A 🔊 volume slider over the office window controls the sound level.
  • It's pure fun, but it genuinely reflects pipeline activity — planning, editing, verifying.

📅Calendar & Cron

Schedule tasks on a calendar, or set recurring cron jobs that auto-create To Do cards and start them.

Cards on the calendar

  • Each entry has a date, optional time, task text, project, priority (color-coded), and an optional cron expression.
  • Schedule label (optional, e.g. "Morning standup") — a short name that appears on the ⏰ chip and tooltips so recurring jobs are recognizable on the board.
  • One-off cards fire when their date (and time) arrives; a live preview under the cron input shows the exact next fire moment as you type.

Cron presets

35 presets grouped into 8 categories — Frequency, Daily, Weekdays (Mon–Fri), Weekend, Specific day, Monthly, Yearly, Other. Interval presets (*/15, every hour) install recurring schedules; time-of-day presets clicked when a card already has a date become a one-off fire at that time on that date instead.

Cron syntax

Standard 5-field cron: minute hour day-of-month month weekday. Supports *, */n, ranges a-b, and lists a,b.

ExampleMeaning
0 9 * * 1-5Weekdays at 9:00 AM
0 18 * * 1-5Weekdays at 6:00 PM
0 0 * * 0Every Sunday at midnight
0 0 1 * *First day of the month
*/15 * * * *Every 15 minutes
0 9 1,15 * *1st & 15th at 9 AM

Next-fire hints

Day cells show a subtle amber ⏰ when a schedule lands on them (with a count badge if several fire the same day), computed from the cron expression with the same semantics the processor uses — day-of-month and day-of-week must both match, so the hint always reflects reality.

Run now

The card edit popup has a ▶ Run now button that fires the card immediately — creates the To Do card and starts it, so you can test a schedule without waiting.

Fired cards on the board

Every fired card lands in To Do with ⏰ SCHEDULED (showing its schedule label when set) and the schedule name/expression in its tooltip. If the agent is busy, the card sits READY and the queue picks it up when a run finishes.

💡Suggestions

When a card finishes successfully, Weaver generates 0–3 concrete improvement suggestions for the work.

  • Suggestions are generated from the completed card's task, summary, and edited files — plus a broader view of the whole app: the full project skeleton and the kanban's history (so a suggestion can connect features, e.g. "banning should notify users" after a notifications system was built).
  • Each suggestion carries file attachments (real project paths) as discovery context and a connection line describing which other card/feature it builds on.
  • Suggestions persist on the card and render in the Done column.
  • Clicking a suggestion creates a To Do card pre-filled with the suggestion text (tagged 💡 SUGGESTION), its file attachments, and the source card's completion summary so the agent has full context.

How much whole-app context the suggestion engine sends is a per-project setting — skeleton only, skeleton + board history, or everything including git history (default: full depth).

📊Benchmarks

Automated test harnesses that run real agent tasks against your configured endpoint to measure capability, reliability, and speed.

How they work

  • Each benchmark is a realistic task (create a folder + files, web-search facts, cross-check consistency, call a REST API, etc.) with acceptance checks evaluated against the actual artifacts.
  • Runs are scored with points and a percentage; scores are stored and ranked.
  • Benchmark All runs every level in sequence; the run cards appear on the board with live logs.
  • Levels are served dynamically — new benchmarks appear automatically in the plans list.

Selected levels

LevelTaskChecks
16Pokémon data fetchCSV with ids/stats/types + freshness timestamp
17Web Search 1: sequential factsMultiple independent searches, each written to file + freshness
18Web Search 2: cross-check consistencyReconcile facts across searches into a verdict
19Data Fetch 2: REST weather APIReal cities + JSON fields + freshness (JSON-aware marker)

Fetch freshness

Data-fetch levels demand a run-time timestamp (FETCHED_AT: YYYY-MM-DD, or a JSON "fetched_at" field). A check passes only if the embedded date is within ±1 day of the file's write time and within the freshness window of today — so cached or fabricated runs get flagged, and a hardcoded old date can't slip through.

💡 Benchmarks are the best way to compare endpoints: run the same level against a local llama.cpp server and a hosted API and compare scores side by side.

🏅Ranks

The rank system gamifies your usage. You earn points from completed cards, benchmarks, projects, and archived work, and climb a ladder of titled ranks.

  • Click your rank in the header to open the rank stats popup — progress bar to the next rung, your current score, and the full rank ladder.
  • Each rung has lore (click or press Enter/Space to expand it — rows are keyboard-accessible).
  • An explicit ✕ closes the popup; it also closes on outside blur.
  • Stats include cards done, done this week, daily streak 🔥, best benchmark score, and archived count.
  • Your grade is shown with chevrons/stars on the header badge.

🎤Voice Input

  • Continuous speech recognition with auto-append into the card text field.
  • A recording indicator with a timer while you speak.
  • Auto-restarts on disconnect so long dictation keeps flowing.

🔀Git & PRs

  • Git operations are a first-class agent tool (_git) — commit, push, and branch work.
  • Auto-PR can be toggled per card: when the card completes, Weaver creates a pull request from the changes.
  • The IDE exposes commit/push/PR actions directly.
  • All git commands still respect the terminal approval rules unless approved.
⚠ Weaver never pushes to remote or creates PRs without the relevant approvals in place — but with Approve all + auto-PR enabled, completion of a card can push code. Review the settings if you share a repo.

  • Default LLM Endpoint — the OpenAI-compatible base URL the agent uses.
  • Additional LLM Endpoints — add several endpoints (name, URL, model); each shows a live health badge. Endpoints power concurrent runs and let you compare models.
  • Context Size Limits:
    • Max File Context Chars — how much of a single file the agent reads (4k–64k).
    • Max Full File Tokens — files larger than this are truncated before the agent sees them; keep it high enough for your largest files or edits can miss code.

  • Agent Tools — checkboxes enabling/disabling each step type (explore, discover, command, create, SQL migration, web search, web fetch, git, rename, delete, show).

🔌LLM Endpoints

Weaver speaks the OpenAI-compatible chat API, so it works with llama.cpp, Ollama, LM Studio, or any compatible server — local or hosted.

  • Default: http://localhost:8080 (adjust in Settings → Agent).
  • Multiple endpoints: add several and they appear as options for runs; the header shows the active endpoint with a live health badge (🟢/🟡/🔴).
  • Concurrency: with multiple endpoints, several agent runs can execute at once, each on its own endpoint.
  • If your endpoint is unreachable, run cards fail fast with a connectivity message; the app caches health checks.
💡 Smaller local models benefit from the iterative verify-as-you-go loop — the bigger models simply converge in fewer cycles.

🛡Terminal Security

The approval system sits between the agent and your shell. Three modes:

ModeBehaviorUse when
Approve every commandEvery command waits for your clickYou want maximum control (default-safe)
Approve command rootsOnly exact executables in Approved Roots run unprompted; everything else asksA balance of speed + safety
Approve allEverything runs without askingTrusted, low-risk sandboxes only

Approved Roots / Disallowed Roots — comma-separated executables (e.g. git, dotnet, rg, npm). Approved roots bypass the prompt in root mode; disallowed roots are always rejected. Pending commands show an approval card where you can approve once, approve the root, approve all, or reject.

🧭Using Weaver Without Writing Code

You don't need to be a programmer to use Weaver. Think of it as a very capable assistant living inside an app that can read and edit your files, search the web, send email, and run tasks on a schedule — you just describe what you want.

The mental model

  1. Cards are tasks. Everything starts as a card on the kanban board. Write what you want in plain English.
  2. The agent does the work. When you press Start, the agent reads your request, explores the project, plans, edits files / searches the web / sends email, and verifies its own work.
  3. You stay in control. The agent's every step is visible in the log, and anything risky (terminal commands) waits for your approval.

Your first task, step by step

  1. Make sure Weaver is running and connected to an AI endpoint (see LLM Endpoints).
  2. In the To Do column, click to add a card.
  3. Type something simple: "Create a folder called notes and put a text file in it listing my top 3 goals".
  4. Press Start and watch the Agent panel stream the plan and steps.
  5. When it finishes, check the result in the IDE (left panel) or your filesystem, then move the card to Done.

Safety, in plain English

Weaver can run commands on your computer. By default it asks you before running anything. In Options → Settings → Security you can change this — but if you're not a developer, leave it on Approve every command. When a command asks for approval, read it and click Approve once only if it makes sense (something like npm install or a build is normal; something deleting files is not).

📋Everyday Workflows

Real-world recipes for the things non-programmers ask for most: email, web research, and scheduled tasks.

✉️ Recipe 1 — Send an email with the agent

  1. Connect your mailbox: Options → Settings → 🔗 Integrations → Email (IMAP). Add your email server (for Gmail: imap.gmail.com, port 993, SSL on), your full address, and an app password (generate one in your email provider's security settings — not your normal password). Click Test Connection until it passes, then Save.
  2. Create a card in To Do, e.g. "Send an email to sam@example.com summarizing this week's progress notes".
  3. Attach any files you want included, press Start, and approve any command it asks for.
💡 Emails are composed and sent by the agent through your connected account — always read what it wrote before sending important mail.

📅 Recipe 2 — Set up a recurring task (cron)

  1. Open the Calendar (Options → 📅 Calendar, or the header button).
  2. Click + Add Card, pick a date, write the task (e.g. "Back up my documents folder"), and pick a project.
  3. Give it a Schedule label like "Weekly backup" so you can spot it on the board.
  4. Pick a cron preset — e.g. Weekdays at 9am or Every Sunday — and watch the live preview confirm the next fire time.
  5. Save. At the scheduled moment Weaver creates a To Do card (⏰ SCHEDULED) and starts it automatically.

To test a schedule immediately, open the card and press ▶ Run now.

🌐 Recipe 3 — Research the web and save the results

  1. Create a card: "Search the web for the latest news about [topic], then write a summary file with 5 facts".
  2. Press Start. The agent performs real web searches (a _web_search step) and writes the answer into a file it creates.
  3. Open the file in the IDE to read the result.

☀️ Recipe 4 — A daily digest, fully automatic

  1. Calendar → Add Card → task: "Search the web for today's top AI news and email me a 3-bullet summary".
  2. Schedule label: "Morning digest"; preset: Weekdays at 9am.
  3. Save, then press ▶ Run now once to test it end to end (email + web search both need to be configured).

From then on it runs itself every weekday morning — card created, researched, and emailed without you touching anything.

🗒 Recipe 5 — Take notes by voice

Open the Notes panel, and use the 🎤 voice button to dictate — Weaver transcribes continuously and appends to the note. Great for capturing thoughts while you work.

✅ Recipe 6 — Check that everything works (benchmarks)

Options → 📊 Benchmarks → Benchmark All. Weaver runs a set of practice tasks (create files, fetch web facts, call a weather API) and scores them. If they pass, your setup is healthy — calendar, web search, and file creation will all work.

⚠ Non-programmer safety checklist: keep Terminal Approval on Approve every command; read every approval prompt; never approve a command you don't understand; review emails before they send; and keep your data-folder backups — your cards and settings live in data/weaver.db next to the app.

🏗Project Architecture

A developer's tour of how Weaver is put together: an ASP.NET Core backend serving a static AngularJS frontend, with the agent pipeline split across a family of partial classes and focused services.

Top-level layout

PathWhat lives there
Program.csApp bootstrap: UTF-8 console, --self-check native-lib probe, embedded appsettings.json fallback, data-folder writability guard, startup log, host build.
Controllers/HTTP API — one controller per domain, plus AgentController.*.cs partial classes splitting the agent engine by concern.
Services/Shared engines: SQLite storage, board/calendar persistence, AST editing, code formatting, BM25 discovery, git, terminal, email, push, benchmarks, LLM plumbing.
DataContracts/Typed request/response models (Agent plan steps, edit actions, questions, build checks, …).
Hubs/SignalR hub for real-time shared editing (CoEditHub).
wwwroot/The entire UI: index.html + AngularJS panels (kanban.html, ide.html, notes.html, meeting.html, calendar.html) and controllers/mixins (app.js, agent.js, settings.js, calendar.js, filetree.js), styles, service worker, docs.html.
tests/UnitTests/xUnit tests that compile into the main project and run via dotnet test (see Testing).
tests/js/Dependency-free Node unit tests for frontend JS modules (error-core, meeting-ticker).

Backend bootstrap (Program.cs)

  • --self-check — verifies the bundled native libraries (SQLite + tree-sitter) actually load, exits 0/1. The in-app updater runs a freshly downloaded Weaver.exe with this flag before replacing the running copy, rejecting broken publishes.
  • Embedded appsettings — single-file publish bundles appsettings.json inside the exe; when no on-disk file exists, the embedded copy is loaded (an on-disk file, when present, wins).
  • Data folder — data/weaver.db next to the exe; the app refuses to start with a clear message if that folder isn't writable (e.g. inside Program Files).
  • Startup log — every console line mirrors to data/weaver-startup.log (or %LOCALAPPDATA%/Weaver/ if the data folder is unwritable) for post-crash inspection.
  • UTF-8 console encoding is forced so the welcome banner and emoji log lines render on Windows.

The AgentController partial-class map

One class split across files, each owning a pipeline concern:

Frontend architecture

  • AngularJS 1.8 single-page app: index.html hosts the chrome (header, agent panel, terminal), and feature views are included as separate templates (kanban.html, ide.html, notes.html, meeting.html, calendar.html).
  • Controller mixins — app.js (core/main), settings.js (settings + workspace persistence), agent.js (agent run + kanban orchestration), calendar.js (calendar UI + the cron processor with cronMatches/nextCronFire), filetree.js (IDE explorer).
  • Live streaming — the agent streams progress over SSE (plan events, steps, logs, verify results) into the Agent panel; diffs are previewable and applyable inline.
  • Real-time collaboration — SignalR CoEditHub broadcasts shared-edit indicators for BugHosted sessions.
  • Service worker — service-worker.js + error-core.js for push notifications and resilient error handling.
  • Persistence — settings/panel geometry in localStorage, board/calendar/scores on the backend DB; a hard refresh keeps everything.

The agent pipeline, deep dive

  1. Discover (Phase 1) — enumerate the project, index files, run BM25 to score relevance against the task, auto-read the top files, consult file hints and attached files, and produce a project skeleton. Runs in an isolated sandbox when enabled.
  2. Context review — the agent summarizes what it found; you can auto-confirm (5s) or steer.
  3. Plan & execute (interleaved) — one atomic step at a time: propose → pre-validate → execute → between-steps verify → next. Step proposals are rejected with feedback (e.g. duplicate-file guard: "index.html already exists at benchmark_test_4 — target that path") and re-proposed.
  4. Post-execution verification — a verifier checks the finished work against the explicit requirement checklist and returns concrete issues; speculative complaints are triaged out.
  5. Repair loop — up to 3 passes re-plan for unmet requirements; if the replanner recycles a completed step, corrective feedback names the verifier's concrete unmet requirement instead of burning a pass.
  6. Resume — completed plan steps persist on the card; resuming re-plans for unmet requirements instead of declaring done.

🧪Testing

Weaver ships with a substantial automated suite — 700+ xUnit tests plus frontend Node tests — covering the edit engine, formatters, discovery, the pipeline, and benchmarks.

Run the full suite

dotnet test

Tests live in tests/UnitTests/ and compile into the main project (no separate test csproj) — the xUnit packages are private references in Weaver.csproj, and the SDK's default globs pick up every *Tests.cs file automatically. dotnet test discovers and runs them all.

⚠ While the app is running, Weaver.exe locks the build output. Run tests with a separate output dir to avoid the lock:
dotnet test -o .test-out

Run a subset

Use xUnit's --filter against the class name:

dotnet test --filter "FullyQualifiedName~CodeFormatterServiceTests"
dotnet test --filter "FullyQualifiedName~BenchmarkFreshnessTests"
dotnet test -o .test-out --filter "FullyQualifiedName~FormatCEditTests"

Writing a new test

  1. Add a file tests/UnitTests/YourThingTests.cs using xUnit ([Fact] / [Theory]) and the Weaver namespaces.
  2. It compiles automatically — no project file edits needed.
  3. Run it with the filter above. Follow the existing style: pure unit tests on services where possible (constructor stubs for DatabaseService take (ILogger, options, …) — check an existing test for the shape).
  4. For edit-engine behavior, add a corpus-style test that runs a realistic edit payload and asserts the exact resulting file content.
💡 The corpus and fuzz tests are the highest-value targets when you change the edit pipeline — they pin real-world behavior so refactors can't silently regress formatting or edit application.

🔧Troubleshooting

Agent says it can't reach the LLM

  • Confirm your llama.cpp / Ollama server is running at the configured URL.
  • Check the endpoint's health badge in the header — 🟡/🔴 means unreachable.
  • Verify the endpoint speaks the OpenAI-compatible API (model name may matter).

Edits are wrong or incomplete

  • Raise Max Full File Tokens — truncated files cause incomplete edits.
  • Raise Max File Context Chars if large files matter to the task.
  • Attach relevant files to the card or add file hints so discovery reads the right code.
  • Use steering to correct the agent mid-run.

A card is stuck in Doing

  • If the stream died without a done event, the card is marked interrupted (amber) rather than "running" — just restart it.
  • Stop the run from the agent panel if it's looping, then re-run the card.

The backend won't close

Close the website/tab first — the backend process can remain active after the tab closes. Explicitly closing the interface helps terminate the backend properly.

Verification keeps failing on a file that looks fine

The verifier is intentionally strict and checks the explicit requirement list. Speculative complaints ("might/could") are already triaged out. Check the file for hidden issues (whitespace, casing) and re-run — the repair loop gives 3 passes.

🛠Build & Publish

Everything a developer needs to restore, build, run, test, debug, and ship Weaver — including the single-file publish gotchas.

Requirements

  • .NET 10 SDK (or a compatible runtime for running the published exe)
  • An OpenAI-compatible LLM endpoint (llama.cpp / Ollama / hosted) — optional for building, required for agent features
  • Git Bash (Windows) for ./publish.sh; PowerShell for publish.ps1

Restore, build, run

dotnet restore
dotnet build
dotnet run

Weaver is a standard ASP.NET Core web app: the backend serves the wwwroot/ static UI and the JSON API on the console-printed URL (usually http://localhost:5000). Debug with dotnet run and attach your debugger, or dotnet watch run for live reload while iterating on wwwroot/ files.

Tests

dotnet test

700+ xUnit tests in tests/UnitTests/ compile into the main project (see Testing). While the app is running, use dotnet test -o .test-out to sidestep the exe file lock.

Publish a standalone EXE

dotnet publish -c Release -r win-x64

Configured in Weaver.csproj: single-file, self-contained, with the native libraries (e_sqlite3, tree-sitter) and the web UI bundled inside Weaver.exe. Everything extracts to %TEMP%/.net/Weaver/ on first launch, and the app creates its data/weaver.db next to the exe — so the folder must be writable.

  • Recommended one-command flow: ./publish.sh (Git Bash) or publish.ps1 (PowerShell). It publishes, fails if any native DLL was left beside the exe, smoke-tests the lone exe from an empty temp folder (server must stay up and log the welcome banner), and prints the SHA-256 ready for upload.
  • Don't use /p:PublishSingleFile=true on the CLI — MSYS in Git Bash rewrites /p: paths; the flag is already in the csproj.
  • Keep trimming off. The exe is ~200 MB on purpose: tree-sitter, AngleSharp, and MailKit are reflection-heavy and break under PublishTrimmed.

Sanity-check a build: --self-check

Weaver.exe --self-check

Loads the bundled native libraries (SQLite + tree-sitter) and exits 0 on success or 1 on failure. The in-app updater runs a freshly downloaded Weaver.exe with this flag before replacing the running copy — a stale partial publish (natives not bundled) fails here and is rejected instead of being shipped.

Runtime configuration

appsettings.json is embedded in the published exe (an on-disk copy, when present, wins). The keys the app reads:

KeyDefaultPurpose
Editor:WorkspaceRoot..Default workspace root for the file explorer.
Editor:ShowDeleteConfirmationtrueConfirm before deleting files in the IDE.
Editor:PopupBlurBackgroundtrueDim the app behind popups.
Editor:DisableLLMRetriesfalseTurn off automatic LLM retries (diagnostics).

User settings (endpoints, limits, theme, approvals) live in the weaver_config table of data/weaver.db — there is no weaverconfig.json anymore.

Logs & troubleshooting

  • Startup log: data/weaver-startup.log (mirrors the console; falls back to %LOCALAPPDATA%/Weaver/ when the data folder is unwritable).
  • If the app flashes and exits, the folder next to the exe is likely unwritable — move it somewhere writable.
⚠ The exe must remain untrimmed and must bundle its natives — the publish.sh / publish.ps1 scripts enforce both, and --self-check verifies them at runtime.

❓FAQ

Where do I start?

Open Options (top right), configure a project and the LLM endpoint, add a card to the kanban, attach files for context, and press Start.

Why is my task routed to chat instead of edits?

Use "Fix the …" phrasing to force the standard file-edit pipeline. Example: "Fix the README.md file to add a new section about forced edits".

What happens when I click a suggestion on a Done card?

A new To Do card is created, tagged 💡 SUGGESTION, pre-loaded with the suggestion text, its file attachments, and the source card's completion summary.

Can I make the agent work overnight?

Yes — the auto-queue keeps pulling READY cards, self-improving cards round-robin, and calendar cron jobs create and start cards on schedule.

Is my data stored locally?

Yes — the database, settings, board data, and your projects live on your machine. Only optional features (BugHosted, version checks, push) talk to the network.

Why is there a gold spider on my screen?

That's the Weaver skulltula — the app's mascot, and the same logo adorns this documentation. It breathes while the agent thinks. 🕷️
